# S0.1 — Catalog Contract

Status: **accepted for S1 implementation**

Module: `org.3mm.store`

This document freezes the first Store-owned catalog contract. It is deliberately
small enough to implement and physically validate before cart, checkout,
customers or payments are introduced.

It does not add Store semantics to 3mm Core.

## 1. S1 scope

S1 implements:

- Store-owned settings required by catalog rendering;
- categories;
- products;
- SKU;
- one Store currency;
- product price in integer minor units;
- basic stock-on-hand inventory;
- operator catalog/inventory management;
- administrator Store settings;
- public home, category and product pages through M19;
- stable slugs and redirect history;
- deterministic package build;
- Store-owned SQLite migrations;
- restart, disable/re-enable and backup/restore acceptance.

S1 intentionally does **not** implement:

- variants/options;
- cart;
- customers/accounts;
- checkout;
- orders;
- taxes/discount calculations;
- payment;
- shipping providers;
- product reviews;
- multi-currency;
- Internet TLS/domain automation.

Variants are deferred rather than half-designed. They will be added by a
forward Store migration when the cart/order model is designed.

## 2. Entity identity

Public/business entities use opaque stable IDs generated by the Store service.

Format:

```text
product:   prd_<32 lowercase hex>
category:  cat_<32 lowercase hex>
media:     med_<32 lowercase hex>
```

Example:

```text
prd_7c86be3be91c49dbac6ab0ae8d78646c
```

Generation uses cryptographically strong randomness such as
`secrets.token_hex(16)`.

Rules:

- IDs never contain business meaning;
- IDs never change when name, slug or SKU changes;
- SQLite row numbers are not public identities;
- the browser cannot choose entity IDs for create commands;
- deleted/archived IDs are never reused.

## 3. Slug contract

S1 canonical slugs are ASCII and lowercase:

```text
^[a-z0-9]+(?:-[a-z0-9]+)*$
```

Maximum length: 120 characters.

Store UI may generate a transliterated slug from a Bulgarian or other Unicode
name, but the final stored canonical slug must satisfy the contract.

Rules:

- product slugs are unique among products;
- category slugs are unique among categories;
- a product and a category may share the same slug because their public route
  namespaces differ;
- changing a slug writes the previous slug to `slug_history`;
- a request using an old slug returns a permanent redirect to the current slug;
- changing a slug never changes the entity ID;
- archived entities keep their slug reservation unless explicitly purged by a
  later reviewed lifecycle policy.

## 4. Money and currency

S1 uses one Store-wide ISO 4217 currency.

Initial default:

```text
EUR
```

The value is Store-owned configuration, not a Core setting.

Persisted money uses integer minor units:

```json
{
  "price_minor": 1299
}
```

With Store currency `EUR`, that means EUR 12.99.

Rules:

- no persisted `float`/binary floating-point money;
- `price_minor >= 0`;
- S1 products inherit the single configured Store currency;
- changing Store currency does not perform conversion;
- changing currency after commercial order functionality exists will require a
  separate migration/business rule in a later stage;
- historical orders in S2+ will snapshot their own currency and accepted line
  amounts.

## 5. Store-owned configuration

S1 settings live inside Store-owned SQLite and are changed through declared
administrator operations.

Initial keys:

```text
store_name
currency
public_base_url
```

Semantics:

- `store_name`: public display name;
- `currency`: three-letter uppercase ISO currency code, initially `EUR`;
- `public_base_url`: optional trusted canonical origin used for absolute
  canonical URLs and structured metadata.

`public_base_url` is never inferred from an arbitrary public `Host` header.

Manifest configuration remains reserved for platform-owned bindings and is not
used as a general Store-settings database.

## 6. S1 SQLite schema

All tables below live in the Store Application Extension
`ApplicationStorage` database.

The migration revision starts at:

```text
0001
```

### 6.1 `store_settings`

```sql
CREATE TABLE store_settings (
    key TEXT PRIMARY KEY,
    value_json TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

Only Store-known setting keys are accepted by the service. Arbitrary keys from
the browser are rejected.

### 6.2 `categories`

```sql
CREATE TABLE categories (
    id TEXT PRIMARY KEY,
    slug TEXT NOT NULL UNIQUE,
    name TEXT NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    parent_id TEXT NULL REFERENCES categories(id) ON DELETE RESTRICT,
    sort_order INTEGER NOT NULL DEFAULT 0,
    status TEXT NOT NULL DEFAULT 'active'
        CHECK (status IN ('active', 'archived')),
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE INDEX idx_categories_parent_sort
    ON categories(parent_id, sort_order, name);
```

Rules:

- category cycles are rejected by service validation;
- an archived parent cannot receive a new active child;
- deletion is not an S1 operation; archive is used instead.

### 6.3 `products`

```sql
CREATE TABLE products (
    id TEXT PRIMARY KEY,
    sku TEXT NOT NULL UNIQUE,
    slug TEXT NOT NULL UNIQUE,
    name TEXT NOT NULL,
    short_description TEXT NOT NULL DEFAULT '',
    description TEXT NOT NULL DEFAULT '',
    status TEXT NOT NULL DEFAULT 'draft'
        CHECK (status IN ('draft', 'active', 'archived')),
    price_minor INTEGER NOT NULL
        CHECK (price_minor >= 0),
    track_inventory INTEGER NOT NULL DEFAULT 1
        CHECK (track_inventory IN (0, 1)),
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);

CREATE INDEX idx_products_status_name
    ON products(status, name);

CREATE INDEX idx_products_updated
    ON products(updated_at);
```

SKU rules:

- trimmed;
- 1–80 characters;
- case-insensitive uniqueness is enforced by service normalization;
- canonical stored SKU is uppercase for S1;
- allowed characters: `A-Z`, `0-9`, `-`, `_`, `.`.

Product lifecycle:

```text
draft -> active -> archived
draft -> archived
archived -> draft
archived -> active
```

Public rendering returns products only when status is `active`.

### 6.4 `product_categories`

```sql
CREATE TABLE product_categories (
    product_id TEXT NOT NULL
        REFERENCES products(id) ON DELETE CASCADE,
    category_id TEXT NOT NULL
        REFERENCES categories(id) ON DELETE RESTRICT,
    sort_order INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (product_id, category_id)
);

CREATE INDEX idx_product_categories_category
    ON product_categories(category_id, sort_order, product_id);
```

A product may belong to multiple categories.

S1 does not define a "primary category" because canonical product URLs do not
depend on category hierarchy.

### 6.5 `inventory`

```sql
CREATE TABLE inventory (
    product_id TEXT PRIMARY KEY
        REFERENCES products(id) ON DELETE CASCADE,
    stock_on_hand INTEGER NOT NULL DEFAULT 0
        CHECK (stock_on_hand >= 0),
    updated_at TEXT NOT NULL
);
```

S1 inventory has no reservations because cart/order behavior does not exist yet.

Public availability is derived as:

```text
track_inventory = false -> available
track_inventory = true and stock_on_hand > 0 -> available
track_inventory = true and stock_on_hand = 0 -> out_of_stock
```

The public browser never supplies authoritative stock.

### 6.6 `product_media`

The metadata contract is frozen now even though normal media ingestion remains
a platform-gap item.

```sql
CREATE TABLE product_media (
    id TEXT PRIMARY KEY,
    product_id TEXT NOT NULL
        REFERENCES products(id) ON DELETE CASCADE,
    storage_key TEXT NOT NULL UNIQUE,
    media_type TEXT NOT NULL
        CHECK (media_type IN ('image/jpeg', 'image/webp', 'image/avif', 'image/png')),
    byte_size INTEGER NOT NULL
        CHECK (byte_size > 0),
    width INTEGER NOT NULL
        CHECK (width > 0),
    height INTEGER NOT NULL
        CHECK (height > 0),
    sha256 TEXT NOT NULL,
    alt_text TEXT NOT NULL DEFAULT '',
    sort_order INTEGER NOT NULL DEFAULT 0,
    is_primary INTEGER NOT NULL DEFAULT 0
        CHECK (is_primary IN (0, 1)),
    created_at TEXT NOT NULL
);

CREATE INDEX idx_product_media_product
    ON product_media(product_id, sort_order, id);
```

`storage_key` is an extension-private relative key below
`ApplicationContext.data_dir`; it is never a caller-controlled absolute path.

Only one media row per product may be treated as primary by service logic.

### 6.7 `slug_history`

```sql
CREATE TABLE slug_history (
    entity_type TEXT NOT NULL
        CHECK (entity_type IN ('product', 'category')),
    entity_id TEXT NOT NULL,
    old_slug TEXT NOT NULL,
    created_at TEXT NOT NULL,
    PRIMARY KEY (entity_type, old_slug)
);

CREATE INDEX idx_slug_history_entity
    ON slug_history(entity_type, entity_id);
```

Before accepting a new slug, Store checks both current slugs and historical
slugs for that entity type so an old URL cannot silently start resolving to a
different entity.

### 6.8 `idempotency_records`

The 3mm host requires idempotency keys for commands; the Store service remains
responsible for replay-safe business behavior.

```sql
CREATE TABLE idempotency_records (
    operation_id TEXT NOT NULL,
    actor_key TEXT NOT NULL,
    idempotency_key TEXT NOT NULL,
    request_hash TEXT NOT NULL,
    response_json TEXT NOT NULL,
    created_at TEXT NOT NULL,
    PRIMARY KEY (operation_id, actor_key, idempotency_key)
);
```

For operator/admin commands, `actor_key` is derived from the authenticated
platform context, not from request payload.

Replay rules:

- same operation + actor + key + same request hash -> return stored response;
- same operation + actor + key + different request hash -> reject;
- a command commits its business mutation and idempotency response atomically.

Retention of old S1 idempotency records may be bounded by a later internal job
once real workload is measured.

## 7. S1 permissions

S1 declares two operator permissions:

### `catalog_manage`

Allows daily catalog work:

- create/update/archive categories;
- create/update/change product status;
- assign categories;
- read the management catalog.

### `inventory_manage`

Allows:

- read stock;
- adjust stock-on-hand.

Administrator audience may perform these operations through the administrator
gateway without introducing Store-specific Core roles.

Store settings remain administrator-only in S1.

## 8. Compiled UI routes

S1 uses compiled UI.

Planned route entrypoints:

| route_id | entrypoint_id | route | audience | permission |
| --- | --- | --- | --- | --- |
| `catalog` | `catalog` | `/store/catalog` | operator | `catalog_manage` |
| `inventory` | `inventory` | `/store/inventory` | operator | `inventory_manage` |
| `settings` | `settings` | `/store/settings` | administrator | none |

Authorization is declared in `application-extension.json`; Vue route
visibility is not the security boundary.

## 9. S1 operation contract

Exact JSON schemas will be written in the package contract during S1
implementation, but S0.1 freezes the operation inventory and audience.

### Internal

| operation_id | kind | audience | permission | idempotency |
| --- | --- | --- | --- | --- |
| `health` | query | internal | none | forbidden |

### Catalog

| operation_id | kind | audience | permission | idempotency |
| --- | --- | --- | --- | --- |
| `catalog_list_products` | query | operator, administrator | `catalog_manage` | forbidden |
| `catalog_get_product` | query | operator, administrator | `catalog_manage` | forbidden |
| `product_create` | command | operator, administrator | `catalog_manage` | required |
| `product_update` | command | operator, administrator | `catalog_manage` | required |
| `product_set_status` | command | operator, administrator | `catalog_manage` | required |
| `catalog_list_categories` | query | operator, administrator | `catalog_manage` | forbidden |
| `category_create` | command | operator, administrator | `catalog_manage` | required |
| `category_update` | command | operator, administrator | `catalog_manage` | required |
| `category_set_status` | command | operator, administrator | `catalog_manage` | required |

### Inventory

| operation_id | kind | audience | permission | idempotency |
| --- | --- | --- | --- | --- |
| `inventory_list` | query | operator, administrator | `inventory_manage` | forbidden |
| `inventory_adjust` | command | operator, administrator | `inventory_manage` | required |

`inventory_adjust` accepts a signed integer delta plus a bounded reason. The
service computes the resulting value transactionally and rejects results below
zero.

It does not accept a browser-calculated resulting stock value as truth.

### Store settings

| operation_id | kind | audience | permission | idempotency |
| --- | --- | --- | --- | --- |
| `store_settings_get` | query | administrator | none | forbidden |
| `store_settings_update` | command | administrator | none | required |

### Public rendering

| operation_id | kind | audience | permission | idempotency |
| --- | --- | --- | --- | --- |
| `render_public` | query | public | none | forbidden |

`render_public` uses the **exact** Application Public HTTP v1 input/output
schemas required by 3mm.

No custom Store HTTP request envelope is introduced.

## 10. Pagination and list bounds

Every catalog/inventory list is bounded.

S1 defaults:

```text
default page size: 20
maximum page size: 100
```

Stable list ordering uses an explicit sort plus entity ID as final tie-breaker.

Supported initial product sorts:

```text
name_asc
name_desc
updated_desc
sku_asc
```

Search input is bounded to 120 characters.

S1 management search matches normalized SKU and name. Full-text search is not
required.

Public category pages use Store-selected deterministic ordering and never
return an unbounded product list.

## 11. Public HTTP routes

S1 declares only the routes needed to prove a real catalog website:

| route_id | path | methods | result |
| --- | --- | --- | --- |
| `home` | `/` | GET, HEAD | public Store home |
| `product` | `/products/{slug}` | GET, HEAD | product page or redirect/404 |
| `category` | `/categories/{slug}` | GET, HEAD | category page or redirect/404 |

All three dispatch to `render_public`.

Allowed S1 content type:

```text
text/html; charset=utf-8
```

Behavior:

- active entity -> 200;
- historical slug -> 301 to current canonical path;
- unknown or non-public entity -> 404;
- HEAD returns the same status/headers/content length without a response body;
- public pages never expose draft/archived product content;
- no Store route is registered directly in FastAPI/Core.

`robots.txt`, sitemap/feed resources and richer metadata remain S6 concerns
unless they are added later as an isolated Store-only increment using the
already accepted M19 contract.

## 12. Public rendering data rules

S1 public pages may include:

- Store name;
- product/category name and description;
- SKU where the Store chooses to display it;
- formatted price based on Store currency;
- derived availability;
- canonical URL based on trusted Store-owned `public_base_url`;
- product media only after the media ingestion/serving path is accepted.

Public pages must not include:

- internal database paths;
- Core/Admin authentication data;
- raw exceptions;
- application socket/runtime details;
- archived/draft catalog records.

## 13. Media boundary decision

S0.1 confirms that **normal product-media ingestion is not yet covered by a
good generic Application Extension contract**.

Current constraints relevant to Store:

- Application Extension RPC messages are capped at 1 MiB;
- M19 public response bodies are capped at 512 KiB;
- no generic Application Extension multipart/media-upload route exists;
- extension `data/` is already included in application backup/restore.

A small base64 image could technically be pushed through an ordinary operation,
but making that the permanent media architecture would couple binary upload to
the JSON RPC limit and is not accepted as the Store design.

Therefore:

- the `product_media` metadata/storage contract is frozen;
- S1 catalog implementation may proceed without product image upload;
- a separate generic **extension media** contract should be designed before
  product media is considered complete;
- that platform work must support arbitrary Application Extensions, not
  `/api/store/upload`;
- no Store-specific Core media endpoint is permitted.

This is a platform-gap candidate, not a reason to block the database/catalog
service work.

## 14. Store transaction rules

Store mutations use `ApplicationContext.storage.transaction()`.

Atomic examples:

### Create product

One transaction commits:

- product row;
- inventory row;
- category links;
- idempotency record.

### Update slug

One transaction commits:

- previous slug to `slug_history`;
- new current slug;
- idempotency record.

### Inventory adjustment

One transaction commits:

- validated stock delta;
- updated timestamp;
- idempotency record.

A partially applied command is not considered successful.

## 15. Time representation

Persist UTC timestamps as normalized ISO 8601 text.

Example:

```text
2026-10-07T05:30:00+00:00
```

Business logic uses the SDK clock where deterministic testing matters.

Display timezone belongs to Store/UI configuration and does not change stored
UTC timestamps.

## 16. Validation boundaries

S1 service validates domain constraints even after Core validates the operation
schema.

Examples:

- ID shape;
- slug shape;
- SKU shape;
- string length;
- currency code;
- category cycle prevention;
- entity lifecycle transition;
- non-negative price;
- inventory cannot fall below zero;
- referenced categories exist;
- archived category/product visibility rules;
- idempotency request hash.

Core remains responsible only for the generic operation contract, audience,
permission and transport boundaries.

## 17. Backup and lifecycle

S1 persistent state is below the Store application `data/` subtree.

Expected backup content:

```text
data/state.sqlite3
data/files/...     # once media is implemented
```

Disable:

- stops Store service;
- removes Store compiled/public routes from active use;
- preserves Store data.

Upgrade:

- applies forward migration;
- must become healthy before activation succeeds;
- failed candidate preserves/restores the previous healthy package according to
  the platform lifecycle.

Store code never performs its own systemd lifecycle or Core database backup.

## 18. S1 acceptance target

S1 is accepted when all of the following pass without Store-specific Core code:

1. deterministic Store package validates and installs;
2. service health becomes ready;
3. operator with `catalog_manage` can create/update/archive categories and
   products without global admin;
4. operator without the permission is denied;
5. `inventory_manage` is independently enforced;
6. product/category records survive service and Core restart;
7. public `/`, product and category pages render through M19;
8. draft/archived entities are not publicly exposed;
9. old slug redirects work;
10. money remains integer minor units;
11. duplicate command idempotency returns the same stored result;
12. conflicting reuse of an idempotency key is rejected;
13. disabling Store removes its active routes while preserving data;
14. re-enable restores service/routes;
15. Store service failure leaves 3mm Admin/Core healthy;
16. backup/restore preserves the S1 database;
17. no code path depends on legacy `/api/store/*` Core behavior.

Product media upload is accepted separately after the generic media boundary is
resolved.

## 19. S0.1 conclusion

Catalog/admin CRUD and public catalog rendering fit the current generic 3mm
Application Extension + M19 architecture.

No Store-specific Core change is required for:

- S1 product/category persistence;
- prices;
- inventory;
- operator/admin management;
- public HTML catalog pages;
- slug redirects;
- lifecycle and backup.

The only newly confirmed S1-adjacent platform gap is robust extension media
ingestion/serving. It remains generic and separately scoped.
